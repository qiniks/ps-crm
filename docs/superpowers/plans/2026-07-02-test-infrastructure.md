# Test Infrastructure (Vitest + React Testing Library) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a working Vitest + React Testing Library harness so every subsequent plan (dependency upgrade verification, Supabase Auth, TanStack Query migration) can follow real red-green TDD instead of manual-only verification.

**Architecture:** Vitest as the test runner (Vite-based, fast, native ESM/TS support, no separate Babel/ts-jest config needed) with the `jsdom` environment for anything that touches the DOM, plus React Testing Library for rendering components the way a user interacts with them and `@testing-library/jest-dom` for readable DOM matchers (`toBeInTheDocument()`, etc.).

**Tech Stack:** vitest 4.1.9, @testing-library/react 16.3.2, @testing-library/jest-dom 6.9.1, @testing-library/user-event 14.6.1, jsdom 29.1.1, @vitejs/plugin-react 6.0.3.

**Sequencing:** This plan must land first — every other plan in this initiative (`2026-07-02-dependency-upgrade.md`, `2026-07-02-supabase-auth.md`, `2026-07-02-tanstack-query-migration.md`) assumes `npm test` works.

**Note on TDD:** Tasks 1–2 below are build-tooling setup (installing a test runner, writing its config) — there is no application behavior to write a failing test against yet, so the Iron Law's "no production code without a failing test" doesn't apply to them (same category as the "configuration files" exception the TDD skill itself calls out). Task 3 is the first real test and is where the red→green cycle starts, deliberately: the test file is written and run *before* the config exists, so the first failure is genuine ("Vitest can't run this yet"), then it turns green once configured.

### Task 2: Vitest config + jsdom setup file

**Files:**
- Create: `vitest.config.ts`
- Create: `vitest.setup.ts`

- [ ] **Step 1: Create the Vitest config**

Create `vitest.config.ts`:

```ts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";
import path from "node:path";

export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    setupFiles: ["./vitest.setup.ts"],
    globals: true,
  },
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
});
```

This mirrors the `@/*` → `./src/*` path alias already declared in `tsconfig.json` so test files can `import { formatMoney } from "@/lib/format"` exactly like application code does.

- [ ] **Step 2: Create the jsdom setup file**

Create `vitest.setup.ts`:

```ts
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

afterEach(() => {
  cleanup();
});
```

`cleanup()` unmounts any component rendered by a previous test — without this, component tests in Task 3 of the Supabase Auth plan (the login form test) would leak DOM nodes between tests and produce false "found 2 elements" failures.

- [ ] **Step 3: Verify the config loads with no test files yet**

Run: `npx vitest run`
Expected: Vitest starts, reports `No test files found`, and exits with a non-zero code (this is expected — there's nothing to test yet, but a clean "no tests found" message proves the config itself parses and the jsdom/react-plugin setup didn't crash on load; a stack trace here would mean the config is broken).

- [ ] **Step 4: Commit**

```bash
git add vitest.config.ts vitest.setup.ts
git commit -m "Add Vitest config with jsdom environment"
```

### Task 3: First real test — prove the harness executes against real code

**Files:**
- Create: `src/lib/format.test.ts`

`src/lib/format.ts` already exists and is correct (three pure functions: `formatMoney`, `formatDuration`, `computeCost`, no dependencies, no mocking needed). This task backfills tests for that existing code — not new TDD-driven behavior — specifically to prove the harness runs against real application code before anything else in this initiative depends on it.

- [ ] **Step 1: Write the test file**

Create `src/lib/format.test.ts`:

```ts
import { describe, expect, it } from "vitest";
import { computeCost, formatDuration, formatMoney } from "./format";

describe("formatMoney", () => {
  it("groups thousands using the ru-RU locale", () => {
    // Intl's exact thousands-separator character varies by ICU data (regular vs.
    // narrow no-break space) — normalize all whitespace before comparing so this
    // test doesn't depend on which one the running Node build ships.
    const result = formatMoney(1234567).replace(/\s/g, " ");
    expect(result).toBe("1 234 567");
  });
});

describe("formatDuration", () => {
  it("formats milliseconds as H:MM:SS", () => {
    expect(formatDuration(3_725_000)).toBe("1:02:05"); // 1h 2m 5s
  });

  it("clamps negative durations to zero instead of going negative", () => {
    expect(formatDuration(-5000)).toBe("0:00:00");
  });
});

describe("computeCost", () => {
  it("computes cost from elapsed hours times the hourly rate, rounded", () => {
    const start = new Date("2026-01-01T10:00:00Z");
    const end = new Date("2026-01-01T11:30:00Z"); // 1.5 hours elapsed
    expect(computeCost(start, end, 200)).toBe(300); // 1.5 * 200
  });
});
```

- [ ] **Step 2: Run it and confirm it passes**

Run: `npx vitest run src/lib/format.test.ts`
Expected: `Test Files 1 passed (1)`, `Tests 4 passed (4)`. If any of these fail, the harness or the alias config (Task 2) is wrong — do not "fix" `format.ts` to match a wrong expectation, since `format.ts` is pre-existing, already-correct, already-in-production code.

- [ ] **Step 3: Run the full suite via the npm script**

Run: `npm test`
Expected: same result as Step 2, confirming the `"test": "vitest run"` script (Task 1) actually picks up the file.

- [ ] **Step 4: Commit**

```bash
git add src/lib/format.test.ts
git commit -m "Add first Vitest test, backfilled against existing format helpers"
```
